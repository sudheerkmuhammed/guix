\chapter{Channels, Pins, and Time Travel}
\label{chap:channels-time-travel}

\epigraph{``Time travel used to be thought of as just science fiction, but Einstein's general theory of relativity allows for the possibility of warping spacetime... and GNU Guix implemented it in Scheme.''}{--- Stephen Hawking (paraphrased by a Guix hacker)}

\noindent
In standard Linux distributions, the concept of ``updating your packages'' is a one-way street into the unknown. When you type \texttt{apt update}, you fetch whatever package definitions happen to be on Debian's mirrors right now. If a scientist wrote code against Python 3.8 and Scipy 1.4 in 2020, attempting to run that same code on an updated 2026 system will usually result in an avalanche of syntax errors, deprecated APIs, and broken wheels.

In GNU Guix, the package collection itself is versioned as a Git repository. Updating Guix is not a chaotic roll of the dice; it is a tracked, reproducible Git checkout called a \textbf{Channel}.

\section{The Heartbeat: \texttt{guix pull}}

To update your Guix package definitions and the \texttt{guix} binary itself, you run:

\begin{lstlisting}[style=guixcli]
guix pull
\end{lstlisting}

Unlike \texttt{apt update} (which merely downloads package indices), \guixcmd{guix pull} downloads the latest Guile Scheme source files from the official Guix Git repository, verifies their cryptographic OpenPGP signatures against a trusted keyring, compiles the Scheme modules with GNU Guile's optimizing byte-compiler, and creates a new generation of your Guix tool itself!

\begin{alchemybox}[Channel Authentication \& The OpenPGP Web of Trust]
How do you know an attacker hasn't compromised the Guix Git repository and injected malicious package recipes?
Guix includes built-in OpenPGP authentication. Every commit in the official Guix channel must be signed by an authorized maintainer. When you run \guixcmd{guix pull}, Guix verifies the signature chain all the way back to the channel's historic ``introduction commit''. If an unsigned or unauthorized commit is pushed, \guixcmd{guix pull} refuses to execute it.
\end{alchemybox}

\section{Declaring Channels in Scheme}

You can customize where Guix pulls its packages from by creating a channels configuration file at \texttt{\textasciitilde/.config/guix/channels.scm}.

Here is an example of declaring multiple channels: the official GNU Guix channel and a custom organizational channel:

\begin{lstlisting}[style=guixscheme]
;; ~/.config/guix/channels.scm
(list (channel
        (name 'guix)
        (url "https://git.savannah.gnu.org/git/guix.git")
        (branch "master")
        ;; Cryptographic introduction to authenticate every commit
        (introduction
          (make-channel-introduction
            "9edb3f66fd80fdac9e8b0f7b442a030d125b6dd7"
            (openpgp-fingerprint
              "BBB0 2DDF 2CEA F6A8 0D1D  E643 A2A0 6DF2 A33A 54FA"))))

      ;; An external or third-party channel
      (channel
        (name 'nonguix)
        (url "https://gitlab.com/nonguix/nonguix")
        (introduction
          (make-channel-introduction
            "f26715f...commit-hash..."
            (openpgp-fingerprint
              "2A39 3FFF 68F4 EF7A 3D29  12AC 040F D0D4 8845 7307")))))
\end{lstlisting}

Whenever you run \guixcmd{guix pull}, Guix will pull, authenticate, and merge the package definitions from all declared channels into your global package namespace.

\section{Capturing Your Exact State: \texttt{guix describe}}

How do you communicate the exact state of your operating system or software environment to a colleague on the other side of the planet?

You run:

\begin{lstlisting}[style=guixcli]
guix describe -f channels
\end{lstlisting}

This produces an exact, machine-readable Scheme file representing the precise Git commit hashes of all active channels:

\begin{lstlisting}[style=guixscheme]
;; Output from guix describe -f channels
(list (channel
        (name 'guix)
        (url "https://git.savannah.gnu.org/git/guix.git")
        (commit
          "a84ef2b9d31b0b571120468307612f0c7f216e87")
        (introduction
          (make-channel-introduction
            "9edb3f66fd80fdac9e8b0f7b442a030d125b6dd7"
            (openpgp-fingerprint
              "BBB0 2DDF 2CEA F6A8 0D1D  E643 A2A0 6DF2 A33A 54FA")))))
\end{lstlisting}

If you save this output to a file named \texttt{channels.scm} and commit it to your Git repository, your project's dependency universe is now locked forever with mathematical certainty.

\section{The Superpower: \texttt{guix time-machine}}

Now comes the coup de gr\^ace that makes every other package manager look like an antique.

Suppose you have a \texttt{channels.scm} file from June 2022. You want to run a pipeline with the exact tools and library versions defined in that commit, but you are currently sitting on a modern system in 2026.

Do you have to install an old Ubuntu 20.04 virtual machine? No.
Do you have to search Docker Hub for an abandoned 6-year-old image? No.

You simply invoke \guixcmd{guix time-machine}:

\begin{lstlisting}[style=guixcli]
# Run an ad-hoc shell using the package universe from channels.scm
guix time-machine -C channels.scm -- shell python-numpy r-ggplot2 -- R

# Or travel to a specific historic commit on the fly!
guix time-machine --commit=a84ef2b9d3... -- install emacs
\end{lstlisting}

\begin{tearsbox}[Scientific Reproducibility: A Solved Problem]
In 2016, a survey in \emph{Nature} revealed that over 70\% of researchers had failed to reproduce another scientist's computational experiments. The culprit was almost always dependency drift: updated libraries changing numerical outputs or missing legacy dependencies.

With \guixcmd{guix time-machine}, scientific pipelines written 10 years ago can be re-executed today bit-for-bit, producing the identical binary results.
\end{tearsbox}

\begin{protipbox}[Testing Upcoming Patches]
You can use \guixcmd{guix time-machine} to test a patch or branch of the Guix repository before pulling it globally into your user profile:
\begin{lstlisting}[style=guixcli]
guix time-machine --url=https://github.com/myuser/guix --branch=fix-my-package \
  -- build my-package
\end{lstlisting}
This allows you to test bleeding-edge packages in total isolation!
\end{protipbox}
